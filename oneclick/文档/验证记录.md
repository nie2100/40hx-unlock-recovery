并入时**发现并修掉的两个假失败**（都会让用户以为装坏了，都是这一轮实测才暴露的）：

1. `RunPostBind.cmd` 的“驱动自愈源”重写判断：包里的模板**本来就写着本机路径**（`%ProgramData%\CMP40HXGen2\drivers` 等是常量），
   于是 `if ($replaced -eq $text) { Bad ... }` 每次 Install/Repair 都会假报一项失败、退出码变成 1。
   现在内容没变时会再判一次“目标行是否已经是本机路径”：是 → 报 OK（幂等），不是 → 才报失败。
2. 新路径驱动的“10 秒存活检查”把 `inpoutx64.dll` 也拿到 `System32\drivers` 去找 —— 它本来就不该在那儿，
   于是每次安装都弹一条“被杀软隔离”的假提示 + 一条假待办。现在只检查“本来就该存在”的路径。

## 自检（SelfTest）四段明细

1. **权限**：`SeSystemEnvironmentPrivilege` 启用 OK。
2. **ESP 读写往返**：写入 4KB 随机数据 → 回读一致 → 删除成功；ESP 上两处固件哈希 = `1e9ca43fab3d5ce8…`（OnlyEFI v0.1.1）。
3. **NVRAM 往返**：按现场 ESP 分区构造 42 字节设备路径节点，与固件里**正在使用**的启动项节点（`Boot0003`/`Boot0005`）**逐字节一致**；
   写入临时项 → 逐字节回读一致 → 解析出 `描述/路径` 正确 → 删除 → 确认消失。
4. **BootOrder**：原样写回 + 回读逐字节一致，且写完仍是 `0005,0003,0002`；`BootNext` 为空。

## 过程中发现并修掉的真问题（都是会“静默失败”的那种）

1. **设备路径节点末尾 2 字节不是保留位**：HardDrive 节点 42B = 4B 头 + 4B 分区号 + 8B 起始 LBA + 8B 扇区数 + 16B 分区 GUID + **1B MBRType(0x02=GPT) + 1B SignatureType(0x02=GUID)**。
   第一版写成 `00-00`，自检立刻报“与现场节点不完全一致”；改成 `02-02` 后与固件在用的节点逐字节一致。**抄模板/想当然都会踩这个坑。**
2. **不能抄现成启动项做模板**：本机 NVRAM 里名为 "Windows Boot Manager" 的两条是过期项（GUID `e775e299-…` ≠ 现场 ESP `3f0ea28b-…`，甚至没有 FilePath 节点）。
   现在改为 **从现场 ESP 分区（`Get-Partition` 的 GPT GUID/起始/大小/分区号）构造节点**，并用“与现场启动项逐字节比对”自证。
3. **幂等路径的 PASS 文案不同**：helper 已到 Gen2 时输出 `PASS: already physical Gen2 x16; no writes needed.`，
   只匹配 `PASS: physical Gen2 x16` 会把正常状态误判为 FAIL（第一版 Verify 就误判了）。已改成正则 `PASS:\s*(already\s+)?physical Gen2 x16`，
   同族写法在 `coldboot-report.ps1` 里也一并修掉。
4. **ESP 已挂在别的盘符时 `mountvol <新字母>: /S` 直接报“参数错误”**：现在先扫现有盘符找已挂载的 ESP（判据 `\EFI\Boot` 或 `\EFI\Microsoft`），再尝试新挂载。
   （曾因此让一次安装停在“ESP 挂载失败”。）
5. **`.cmd` 编码不能想当然**：上游 `RunPostBind.cmd` 是 UTF-8，被当 GBK 读回写会把中文注释改坏。现在按 BOM/严格 UTF-8/GBK 自动识别并**原编码写回**。
6. **CRLF + `(?m)$`**：用 `^for %%S in \(.*\) do \($` 替换驱动源行永远匹配不上（`$` 停在 `\n` 前，`\r` 还在），改用 `(?=(\r?$))` lookahead 后正常。
7. **别把裸 `.sys` 拷进包目录/`C:\Temp`**：火绒实测报 `Exploit/Vulndriver.ad` 并秒删（用户已收到弹窗）。
   现在裸驱动只写 `System32\drivers` 与两个 `%ProgramData%` 目录（实测 10 秒后仍在），载荷里是 base64 文本，另有 ESP 兜底源。

## 2026-09-30（第 8 轮：客户机蓝屏事故 —— 移除盲扫 + 加硬护栏 + 默认不再自动 ECAM）

**事故**：第 7 轮为绕开被策略封杀的 WinRing0，让 ECAM 探测去**盲读** `0x80000000…0xF8000000` 一串物理地址找基址。
客户机主板把那片区域里的一个地址解成平台空洞 → 读操作触发平台致命错误 → 现场蓝屏；因错误锁存在 PCIe 根复合体，**之后每次重启都 `WHEA_UNCORRECTABLE_ERROR`**。
（本机之所以没暴露：本机那块 B560M 对同样地址直接让驱动映射失败，所以"看起来安全"—— 这是典型的"在我这台机器上验证不出来"的坑。）

**修法**：
1. **盲扫列表整体删除**。ECAM 基址只允许来自 ① ACPI MCFG 表（`GetSystemFirmwareTable`）② `Win32_PnPAllocatedResource` 中 PCI 根复合体名下的内存资源；两者都拿不到 → 直接判定 ECAM 不可用（**宁可不修**）。
2. **硬护栏**：`MmioRead/MmioWrite/MmioReadN/MmioWriteN` 增加登记表校验 —— 只有登记过的窗口才允许访问，窗口外一律拒绝并记 `[安全护栏] 拒绝访问未登记物理地址 …`。
3. **默认不再自动尝试 ECAM**：`auto` 只走 WinRing0（含备用服务名 `WinRing0_1_2_1` 逃生通道）。ECAM 仅在显式 `-PciBackend ecam` 时才试。
   WinRing0 用不了时，工具明确报"本机 Gen2 本次不修"并安全退出，不再做任何地址尝试。

本机实测：

| # | 场景 | 结果 |
|---|---|---|
| 1 | 正常路径 Apply | `PASS: physical Gen2 x16`、rc=0、**4 秒** |
| 2 | WinRing0 两个服务名都起不来（等价“被策略封杀”） | **9 秒**内 rc=3 + “本机 Gen2 本次不修/算力不受影响”；**没有任何 ECAM 候选或校验读**；护栏零触发（没碰窗口外地址） |
| 3 | MCFG 解析 | 本机 `GetSystemFirmwareTable('ACPI','MCFG')` 返回 0（取不到）→ 说明 ECAM 的“安全基址来源”在不同固件上未必可用，所以更不能把它设为默认路径 |

**教训（已写进排查指引 5.4 与代码注释）**：绝不对未声明物理地址盲读；此类操作在客户机上表现为不可恢复的 WHEA 蓝屏，只能靠“完全断电冷启动”清锁存。

## 第 10 轮 · 2026-10-01（客户反馈「每次重启都要再手动跑一次 一键修复Gen2，Gen2 才生效」）

**结论：是脚本的问题，共 3 个真实缺陷 + 1 个自动化缺口**（都在「开机路径」上；手动跑那条路不经过它们，
所以现象才是「手动跑一次就好」）。全部在本机用真跑复现、修完再真跑回归。

### 缺陷 1：WinRing0 用不了时直接放弃，不回落到 ECAM（`payload\windows\40hx-retrain-inpout.ps1`）
`-PciBackend auto`（开机任务与 一键修复Gen2 都走这个默认值）在 WinRing0 起不来、或 `WinRing0x64.sys` 找不到时 `exit 3`。
而客户机上这两种情况是**常态**：七彩虹 iGame Center 占用公用服务名 `WinRing0_1_2_0`（实测 STOP_PENDING + DISABLED）、
360/火绒/Defender 的「易受攻击驱动」策略把 `WinRing0x64.sys` 清掉。
- **实测（本机）**：把三处 `WinRing0x64.sys` 全部改名（模拟被隔离）→ 跑 `-Apply`
  - 修复前：`EXIT=3`，日志 `>>> WinRing0x64.sys missing and no source`
  - 修复后：`EXIT=0`、`MCFG: 找到 ECAM 基址 0xE0000000` → `ECAM 校验 0xE0000000: 厂商=0x8086 40HX=0x0100 PCI桥=5` →
    `PCI 访问走 ECAM` → `GUARD = PASS` → `PASS: physical Gen2 x16 reached`
- 现规则：`auto` = 先 WinRing0，失败就回落 ECAM；只有显式 `-PciBackend winring0` 才会「失败就退出」。

### 缺陷 2：ECAM 后端其实一直拿不到基址 —— ACPI MCFG 的表 ID 打包错（`GetMcfgBase`）
原写法 provider `0x41435049`（对）+ 表 `0x4D434647`（**错**）。`GetSystemFirmwareTable` 的表 ID 要的是
**签名按内存顺序**的 DWORD：`'MCFG'` = `0x4746434D`。
- **实测（管理员，本机 B560M）**：
  `EnumSystemFirmwareTables(0x41435049)` → `DBGP MCFG FACP APIC HPET …`（表就在系统里）
  `GetSystemFirmwareTable(0x41435049, 0x4D434647)` → `size=0  err=1168 (ERROR_NOT_FOUND)`
  `GetSystemFirmwareTable(0x41435049, 0x4746434D)` → `size=60  entry0 base=0xE0000000`
- 所以上一版（第 8 轮）把「盲扫」收紧成「MCFG / 系统已声明资源」之后，**ECAM 这条路从来没成功过**
  （日志固定出现 `MCFG: 大小为 0，取不到` → `ECAM: 没有拿到任何系统声明过的配置空间基址` → `exit 3`）。
  它是缺陷 1 的兜底，所以两个必须一起修。
- 修法：**不写死 ID** —— 用 `EnumSystemFirmwareTables` 枚举出系统认识的 `MCFG` 那一项（`0x4746434D` 仅作兜底）。
- **安全边界没变**（这点很重要，别误读成回退了第 8 轮的安全修复）：候选地址仍然只来自 ACPI MCFG 与
  `Win32_PnPAllocatedResource` 里 PCI 根复合体名下的内存资源，且读之前先 `Allow-Mmio` 登记该 256MB 窗口，
  **绝不盲扫物理地址**。本机实测 ECAM 读数与 WinRing0 完全一致（guard 全绿、LNKSTA 一致）。

### 缺陷 3：开机路径不做驱动自愈（`payload\windows\RunPostBind.cmd`）
`:heal`（多源自愈 `WinRing0x64.sys`、纠正服务启动类型）原先**只在 legacy 回落分支里**被调用；
首选的新路径跑之前没有任何自愈 → 「杀软清了 .sys 的那次开机」必然失败，
而下一轮手动跑能成功只是因为**上一轮 legacy 分支已经把文件补回来了**。
- 修法：新路径之前加 `call :heal`；并把 `inpoutx64.sys/.dll` 也纳入自愈（普通源 + ESP `\EFI\40HX\drv` 兜底，
  且触发条件从「只缺 WinRing0」扩成「缺三者中任意一个」）。

### 缺陷 4：提前退出不清理临时服务（同文件）
`exit 3` / `exit 13` 是裸 `exit`，此时临时服务 `inpoutx64T`（一个可读写任意物理内存的驱动）已经 create+start → 常驻系统；
更糟的是下一次运行看到「已在运行」就按 `$ioWas` 判定为「不是我起的」→ 永远清不掉。
- 修法：新增 `Cleanup-EarlyExit`，任何提前退出前都 `sc stop` + `sc delete`（实测：修复后 `-PciBackend winring0` 失败退出，
  `inpoutx64T` 状态 = MISSING）。

### 自动化缺口：加一个「登录后 60 秒自动补跑」
新任务 `CMP40HX Gen2 PostBind Logon`（`schtasks /sc onlogon /delay 0001:00 /ru SYSTEM /rl HIGHEST`，动作同一个 `RunPostBind.cmd`）。
- 理由：开机任务是最早的一批（onstart/SYSTEM），客户机上可能因①杀软在开机阶段拦驱动加载（inpoutx64 起不来 → exit 13）
  ②GPU/驱动还没就绪（exit 12）③驱动文件被清掉（exit 3）而失败；而**用户登录后手动跑一次总是成功** —— 那就由系统自己补跑，不让用户点。
- 幂等：已到 Gen2 时工具输出 `PASS: already physical Gen2 x16; no writes needed.`，不做任何写入。
- 任务名含 `CMP40HX Gen2 PostBind`，`RunPostBind.cmd` 的「厂商任务清扫」与安装器的「禁用其它 40HX 任务」
  都显式排除了它（实测日志 `没有发现其它需要禁用的 40HX 任务`）。
- 安装器 `-Mode Check` / `-Mode Verify` 都会报告它是否注册；`-Mode Uninstall` 会一并删除。

**⚠️ 本次踩到并已修复的事故（写下来当教训）**：
第一版用 `icacls "$Path" /inheritance:r /remove:g ... /T /C` 递归收紧权限 —— **`/T` 会对每个"只有继承 ACE"的子文件
执行一次 /inheritance:r，把它们的 DACL 清空** → 连管理员都读不了（文件所有者不是 Administrators，`Remove-Item` 也被拒），
受影响对象 **50 个**（整个 CMP40HXGen2 目录树的文件）。
- 症状：`[IO.File]::ReadAllBytes` 抛"访问被拒绝"；`icacls <file>` 只输出文件名、没有任何 ACE 行；随后的 base64 转换全部失败。
- 修法（唯一有效的组合）：**逐对象 `takeown /f <file> /a` + `icacls <file> /grant "*S-1-5-18:F" "*S-1-5-32-544:F" "*S-1-5-32-545:RX"`**
  （对文件不加 `/T`、也不带 `(OI)(CI)`）。目录级 `/inheritance:r /remove:g` 对**目录本身**是安全的。
- 已把实现改成：**只对目录改 ACL，绝不带 /T**；顺序是"先 grant 显式权限 → 再断继承+删 Users 多余授权 → 再 grant 兜底"；
  并在函数里加了"递归找出读不了的子对象并逐文件修回"的自愈兜底（`顺带修回了 N 个丢权限的文件`）。
- 结论：**ACL 操作是本包第二危险的动作（仅次于改引导）**，`风险与恢复.md` 里已单列风险与回滚。

### 第 12 轮 · 复审（第 3 轮）必修项与修法

第 3 轮收尾复审判定「不可推送」，必修 1 条：它认为我判断"新路径 PASS 属于哪一段"时用了 `$segTime += (& $ParseStartStamp …)`，

**先把前提在本机实测了**：`$a=@(); $a += $null; $a.Count` → **1**（不是 0），`ArrayList.Add($null).Count` → 1 ——
这条必修项的**前提在本机 PS 5.1 上不成立**，原写法不会错位。不过我还是按它的建议改成显式 `ArrayList.Add`（省得以后有人再怀疑），
并顺手修掉自查发现的两个真问题（见下）。

**修法（`Install-40HXUnlock.ps1`）**：
1. 两个数组改用 `New-Object System.Collections.ArrayList` + `[void]….Add(...)`（`Add($null)` 会老老实实加一个空元素，下标永远对齐）；

3. **删掉"用文件时间兜底"的分支** —— 文件时间是"最近有人写过日志"，不能证明那条 PASS 是本次开机写的（本次失败也会让文件变新）→
   现在只要没有一条 PASS 落在"本次开机时间门槛"之内，一律判**本次未落地**（宁严），并且当整份日志一条时间都抠不出来时额外提示"区域格式异常，请把 postbind.log 发回来"。
